# Direct NVIDIA SMLib provider candidate

This isolated candidate exposes the existing versioned box, Boolean, dispose and display-mesh mount protocol through our direct NVIDIA-source WASM build. It retains the whole native BRep for every operation. Each Boolean copies both input BReps in native code before invoking the mutating API. Native handles stay Worker-owned. Its evidence includes `resultKind` (`empty`, `single-material`, `multi-material`), material/void counts, native validity/predicate, bounds, volume and `volumeQuality`. For an empty native BRep bounds are null and the mesh is empty. A cavity remains the original single-material BRep, including its void. Multi-material results remain a native container; the candidate never extracts or heals them. Multi-material plus void retains the whole native result; its Float32 preview is unavailable with reason `material-orientation-unqualified` because native tessellation winding is not qualified. The Float64 tessellation remains display-only and is not manufacturing evidence. NVIDIA says native volume is undefined for a nonmanifold object: the provider does not call the volume API for those results and returns `volume:null` with `native-undefined-nonmanifold`. Mesh reads provide a native Float64 triangle buffer and a separately Worker-validated Float32 preview buffer. If Float32 collapses a triangle or overflows, the display status is unavailable and the native body remains valid; both buffers are transferred into caller custody. All previews are display-only.

This is a candidate, not release qualification: current tests do not establish shared model/history or native save/undo, full cancellation/deadline fault coverage against the actual kernel, tessellation winding for arbitrary geometry, manufacturing accuracy, non-box operations, STEP, or multi-material-with-void support. The previous qualified experimental adapter remains separate. Worker termination invalidates all its handles. Its inherited mount bounds total successful output reservations to eight per evaluation; that is a current resource limit, not a complete CAD capability.

Build the native `raw-provider` CMake target using `research/wasm-solid-contact-20261105/README.md` from that pinned fork; use `CODI_RAW_SMLIB_GLUE=/absolute/path/raw-provider.mjs CODI_RAW_SMLIB_OUTPUT=/absolute/private/output node node_modules/webpack/bin/webpack.js --config modules/engine/raw-smlib/webpack.worker.cjs`. The build verifies glue; Worker verifies WASM. The mount assumes Worker bootstrap is host-trusted and its descriptor records all hashes.

Actual strict-CSP Chromium tests in `test/raw-smlib-provider/` cover cavity, edge multi-region, disjoint empty, reuse of empty in union, mesh and disposal, real microtask cancellation/isolation, and real multi-material-with-void refusal, and an actual Float32-collapsed preview with the original native result retained. The lifecycle test double separately checks protocol busy, deadlines, response binding and failure cleanup; it is not kernel evidence. The supplied `browser-receipt.json` is the real Worker result. Tests use an isolated loopback fixture and separate browser context, not application integration.

The isolated experimental 6c kernel candidate and its current runtime pins, known failures and browser controls are documented in `test/raw-smlib-6c/README.md`. The preceding hashes describe the earlier baseline and remain historical evidence.

The experimental whole-container qualification and exact current Worker pin are recorded in `test/raw-smlib-whole-void/README.md`. Native validation and the finite regression corpus do not prove arbitrary Boolean correctness.
