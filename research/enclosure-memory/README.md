# Enclosure Worker memory observation

This is one bounded R730 run with Chrome for Testing 130.0.6723.116 and Linux 7.0.0-38-generic x86_64, 2026-11-04. The independently reviewed 0e7938ba source candidate supplied the fixture and pinned workers; 63f946c8 is only the pool source reviewed for interpretation. This test creates direct mounts, not the resource pool, authored history, plate geometry, full desktop, production load, or actual 3D printing. Each mount creates a 100/110/120 x70x30 mm enclosure, reads both 28-triangle preview meshes, and remains live until closed. All worker contexts run in one page/renderer and one Chrome process tree. There was no forced garbage collection. One sample was taken after each 1.2-second quiet interval. Each row is a fresh browser context but the browser process was reused, so baselines are not independent cold launches.

The receipt records Linux RSS/PSS and process types per descendant from smaps_rollup, and page performance.memory estimates. RSS sums count shared mappings repeatedly; PSS is apportioned shared resident memory, not a peak or a per-Worker allocation. Page heap is not Worker heap or WASM linear memory. Other users, browser processes outside the parent tree, OS cache, GPU/physical-device pressure and allocator retention were not measured. The sampled page target reported 0/1/2/3/2/1/0 Workers as expected. After browser.close all PIDs recorded in the final descendant snapshot were absent; this checks those processes only. The after-context PSS includes the still-running browser, not all machine memory. No inference is made from GC timing or apparent reclamation about future OOM risk.

Pool implication: current enclosure construction requires a fresh mount; an accepted plate plus an enclosure may own two mounts. A replacement replay that independently builds both can require two additional candidate mounts while the two accepted mounts remain live. A global cap of three cannot guarantee that 2+2 transition, and this isolated test did not exercise that full model. Do not raise a limit based on this one measurement. A candidate solution is a reviewed immutable shared/reference-counted accepted engine owner with explicit revision, cancellation and disposal fences, or a qualified shared-worker composite operation that creates both without exceeding one mount per owner. Existing fresh-enclosure and lifetime-name constraints do not provide either automatically. If a lower-memory policy instead keeps only a detached last-valid preview while rebuilding native results, it must explicitly block native operations and prove failure recovery without presenting stale geometry as current. Full-app, large-model, repeated-edit, concurrency and low-memory-device measurements remain necessary before selecting limits.

Reproduction: use the public-only fixture built from 0e7938ba with test/enclosure-worker/prepare-fixture.cjs and the pinned input assets in the receipt; serve its root with modules/engine/mount/strict-csp-server.py on 127.0.0.1:19974. Launch an owned headless Chromium with an isolated profile and CDP 127.0.0.1:19975, bind its exact root PID as CODI_CHROME_ROOT_PID, and forward both ports to the driver host. Run codi-enclosure-memory.cjs with Puppeteer and node available; process-memory.py is called read-only over SSH on R730. The committed driver differs from the recorded run only by replacing the hard-coded Chrome PID with the required environment variable. Close the owned context, browser, server and tunnel afterward. This exact harness runs sequential scenarios in a reused browser, not a cold-start benchmark.
