# Research-only 3MF Core writer

Placement regression (2026-11-04): `manufacturing-adapter.test.mjs` exports
three synthetic native-box regions in two authored build groups. The independent
Python standard-library reader `validate_placement.py` walks the actual ZIP/XML
component graph and checks every transformed corner against analytic coordinates.
The first region combines a local Z rotation/translation with an authored X
rotation/translation; these noncommuting placements catch reversed composition,
transposition, omitted transforms, or applying placement twice. The other two
regions remain grouped as one build item. All 20 focused writer/adapter/native
envelope tests pass. Run with Node plus Python 3 from the repository root:
`node --test tests/3mf/manufacturing-adapter.test.mjs tests/3mf/core3mf.test.mjs test/project/project-envelope.test.mjs`.
This is serialization and placement evidence using synthetic boxes, not a test
of the current worker enclosure, an inset label, manufacturing mesh quality,
independent lib3mf conformance, or end-to-end My files export.

`web/app/cad/export/core3mf.mjs` is an isolated pure-data writer, not connected to the UI, CAD model, project storage or host files. It does not prove physical printability or slicer-project compatibility. Each input object becomes a mesh resource plus a named component. Explicit authored build groups combine those components into build items; only object-wide core base materials are supported. Names are display names; caller-supplied material and object IDs serve only as local lookup keys and are not serialized as stable 3MF identities. A material's display color is an export property, not a mechanical material definition. Appearance data independent of materials needs separate mapping work.

Input: `{unit, revision, materials:[{id,name,color}], objects:[{id,name,materialId,vertices,triangles,transform}], builds:[{id,name,objects:[objectId,...]}]}`. Multi-object inputs require explicit build groups, and every object must belong to exactly one group. Single-object inputs can omit them. The escaped `revision` is recorded as custom 3MF Core metadata `codi:SourceRevision`; it is caller-provided, not an authenticated provenance claim. Units are explicit 3MF Core names, including `millimeter`. Vertices are model-space `[x,y,z]`, triangles are indexed `[v1,v2,v3]`, and optional transform has 12 row-major 3MF matrix entries with translation in the final three entries. IDs use 1–128 ASCII letters, digits, `_`, `.`, `:`, `-`; material ID can be null. Colors are `#RRGGBB` or `#RRGGBBAA`. Arrays must be pre-welded; exporter never guesses a merge tolerance. A bounded snapshot is taken synchronously before async validation so later caller edits do not alter the export.

The writer checks finite coordinates and transforms, index bounds, non-degenerate faces, exactly two oppositely directed triangles per edge, connected vertex-fan checks, and alternating component volume orientation by verified containment depth. Where component bounds overlap, nesting is supported only for exact axis-aligned box shells (8 corners and 12 triangles); touching, intersecting and ambiguous shell bounds are rejected. Up to 64 disconnected shells are accepted. A single edge-manifold spindle torus that geometrically self-intersects is accepted by a regression explicitly documenting the limitation. These checks do not prove geometric self-intersection freedom, overlapping shells, tolerances, or that geometry matches the CAD B-rep. Arbitrary non-box nested cavity boundaries, reflected or near-singular transforms, per-face material assignment, Unicode surrogate-pair names, open surfaces, and faces not already triangulated are deliberately unsupported. The exact-box test is a constrained prototype and does not qualify real CAD tessellations or other cavity geometries. Failure is explicit; no repair is attempted. Re-export after parameter edits and persistent references need integration testing before use.

Bounds: 32 objects, 128 materials, 150,000 vertices, 250,000 triangles, 48 MiB model XML, and coordinates up to absolute 1e9. JSZip uses STORE; memory remains proportional to mesh, adjacency maps, XML and ZIP. Cancellation is checked between bounded validation chunks and while ZIP generates, but synchronous snapshot and individual JSZip operations cannot be interrupted. Use a worker and test realistic browser memory and disposal before integrating.

Tests (Node 20+, installed existing repository dependencies):

```sh

python3 -m venv /tmp/codi-3mf-validate-venv

CODI_3MF_LIB_PYTHON=/tmp/codi-3mf-validate-venv/bin/python node --test tests/3mf/core3mf.test.mjs
```

Optional independent test uses the 3MF Consortium's lib3mf 2.5.0 reader in strict mode: no warnings, two valid oriented tetrahedron meshes, material mapping/name/colors, named component transforms, separately arranged and grouped build counts, source revision, and a box cavity with a nested island and a disconnected solid. This does not constitute a comprehensive conformance suite or a production geometry qualification. Existing dependency `jszip` is used; no new runtime package is required.

Grouping records the requested structure; it does not test inter-object contact, overlapping regions, gap tolerances, or select which material wins. Consumers and slicers may interpret coincident/overlapping materials differently. A production handoff must validate or clearly report those conditions.

## Experimental native-box extraction

`web/app/cad/export/nativeMeshBox3mf.mjs` is a research-only adapter for a uniquely resolved `NATIVE_MESH_BOX` native mesh shell. It copies the operation's indexed `brepShell.data.__meshWithOrigins.meshData`, never a rendered face view, and translates `Matrix3x4` model location to the 3MF row-major transform. This is not a general kernel tessellator. It trusts the calling resolver's operation type and feature-ID assertion; a future host must obtain those from validated project history/revision and ensure model state is stable throughout extraction. It refuses OCC shapes, boolean operations, merged vertices, and other triangle counts. The writer still runs its validation. This exact planar primitive has no curved tessellation tolerance to choose. OCC's exposed `UpdateTessellation(ptr, deflection)` exists but its update/interrogation, seams, orientation, shape lifetime, and export-grade tolerance are not qualified here. Native booleans and curved bodies are also unqualified.

`native-box-browser.probe.mjs` is an opt-in, loopback-only test: start an isolated prepared runtime and Chromium CDP, install `puppeteer-core` in the test environment, then set `CODI_3MF_CAD_URL`, `CODI_3MF_CDP`, and `CODI_3MF_LIB_PYTHON` before executing it with Node. It invokes the real CAD native box operation inside Chromium, copies the resulting geometry and matrix to Node, runs the adapter and 3MF writer there, and independently reads the result with lib3mf. It checks dimensions, material, and a rotation plus translation. It is not a browser-bundled writer test, not a saved/reopened document test, and does not verify UI or My files. A prior run used the `5713236d` prepared runtime; the native box, native service, model shell, matrix and mesh-builder source files were unchanged between that commit and this branch's base `3b0821df`. The isolated HTTP probe did not reproduce production CSP. Test exact candidate/runtime and the eventual browser integration before release.

## Authored project metadata adapter

`manufacturingTo3mf.mjs` is a research bridge using `resolveManufacturingAssignments` against feature history and the current shell roots. Metadata explicitly groups regions into printable objects; every region currently requires an authored material AND appearance. For 3MF Core, each material/appearance pair is emitted as a distinct base material, but the editable project keeps those identities separate. Each model-space shell location is composed with the authored region transform exactly once. Within a build group, strictly disjoint or boundary-touching transformed bounding boxes are accepted; overlapping bounding boxes are rejected conservatively without selecting a material priority. This can reject physically disjoint rotated shapes; it does not validate physical contact, box intersections between separate build objects, other geometries, or a final print. Only resolved native box features are supported. The adapter recomputes the SHA-256 geometry revision from its captured native project and requires it to match the metadata and supplied revision. This checks integrity against accidental stale assignments but does not authenticate provenance. It synchronously captures model data before asynchronous hashing; a host must recheck that the current project and assignments have not changed before writing an output, and provide safe file persistence before exposing this code.

`manufacturing-model-browser.probe.mjs` exercises two actual native-box features in an isolated staged project, snapshots and restores them in a fresh Chromium workspace, then sends the extracted metadata/history/meshes to the Node adapter and strict lib3mf. The grouped and separate build structures, associated material colors and transforms passed strict independent reader checks on an isolated candidate runtime built from combined source at `7cd2f152`. The subsequent hash-based adapter and snapshot helper additions run on the Node side; their final exact full browser bundle still needs qualification. It is not testing live users, My files, the browser-bundled writer, or physical printing. It does not use display mesh views.

The pinned OCCT interpreter's `Interogate` calls `interrogate(shape, 2, ...)`; that function cleans and remeshes the shape at deflection 2, so calling `UpdateTessellation(ptr, requestedTolerance)` before `Interogate` does not preserve requested tolerance. A proper isolated OCC extraction entry point needs design, ownership, orientation/seam handling, and tests. Do not silently label current display tessellation as requested-tolerance export.

## Controlled enclosure / lid / inset-label experiment

`nativeEnclosureFor3mf` is research-only, limited to the direct subtraction of one strictly inset axis-aligned native box cutter from a native box, open through its top. It checks unique source operations, positive dimensions, indexed mesh bounds and analytical volume before the common writer's topology checks. The adapter requires an explicitly supplied trusted interference verifier for overlapping region bounds and rejects absent, overlapping or uncertain results. The browser probe injects a temporary rectangular-pocket verifier for the example only; no such verifier is registered in product code. **This test-only hypothesis is not a general collision or interface proof and must not be exposed as final behavior.** Bounds and volume do not by themselves prove the whole Boolean mesh has the intended shape. Actual physical material properties, fixture fields and physics are not encoded by 3MF base-material names or colors.

`native-enclosure-browser.probe.mjs` uses an isolated Chromium jSketcher runtime to build seven actual native features: an open enclosure, a separate lid with a recessed pocket, and a box filling that pocket as a different material region. It snapshots the native geometry, wraps/unwraps research metadata in Node JSON, restores into a second workspace, exports in Node, and has lib3mf independently check three valid oriented meshes and two build items. It changes enclosure width 40→44 and lid thickness 2→3, rejects the old revision, restores regenerated history and repeats independent 3MF reading. An overlapping offset label is rejected. This is not host My files, a browser-bundled writer, authenticable provenance, a general interference proof, or manufacturing readiness. The software build served was an isolated runtime built from this research branch with metadata source but the renderer/export code under test ran in Node. Build metadata capture, conflict handling, native project write/read, UI authoring, in-app export lifecycle and independent security review remain necessary.

`manifold-interference.probe.mjs` is an independent Node-only study with the source-built no-eval Manifold engine: a label exactly filling a pocket produced `NoError`, `isEmpty=false`, and volume 0; a clearly displaced overlapping label had volume approximately 5; a 1e-6 overlap had volume approximately 0.00005. A raw `isEmpty` check rejects legitimate contact; a simple positive-volume tolerance can hide small interferences. General validation needs a documented numerical uncertainty and contact policy, checked transformations, topology/geometry provenance, invalid input handling, kernel-status and lifetime handling, and independent edge-case tests. This probe is not wired into export.

`researchManifoldInterference.mjs` is a separate, unregistered fail-closed kernel study. It applies region transforms, refuses coordinates that cannot be represented exactly in Float32, verifies both input kernel statuses and positive volumes, then runs intersection with guaranteed object cleanup. A positive intersection volume returns `overlap`; zero-volume outcomes—including apparent contact or disjoint results—return `uncertain`, never `contact`. `research-interference.probe.mjs` checks overlap, zero-volume outcomes, a sub-Float32 displacement and cancellation with the pinned AOT build. It cannot yet approve an inset contact, prove self-intersection freedom or detect every kernel numerical failure. It performs synchronous kernel operations and must be moved to a bounded worker before any UI integration. The earlier rectangular-pocket fixture verifier remains test-only.
