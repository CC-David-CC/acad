## Five separate questions

1. Data/identity admission establishes schema, finite fields, bounds and unique
   references. It does not prove a nondegenerate entity or solved constraints.
2. Entity/branch domain establishes the supported ordinary positive-size and
   directed Arc meaning. A zero Segment/Circle is not valid merely because it
   has no constraints or every coincidence equation has zero residual.
3. Constraint admission checks original equations/domain/residuals and retains
   accepted relationships. Failed convergence is not global inconsistency.
4. Derived profile/kernel construction is separate: an ordinary open Segment
   is valid sketch geometry but may supply no closed region/solid. Equal
   coordinates do not merge authored IDs or add a PCoincident relationship.
5. Publication/history/persistence must preserve the accepted document on
   refusal and restore actual authored source after normal Save/Open. Parser
   success alone is not successful complete model adoption.

## Current supported semantics and confirmed discrepancy

`headless/primitiveTransition.ts` checks Segment length>1e-9mm, Circle radius
>1e-9mm and at most1e8mm, and Arc endpoint radii>1e-9mm, agreeing within1e-9mm.
Coordinates are finite and bounded1e8mm. Those are existing bounded operation
contracts, not claims that every smaller positive mathematical entity is zero.
`headless/solve.ts::typeIndex` checks the same nondegenerate ordinary entity
minimums before and after solving; solve's independent global bounds remain.

Native Arc is CCW a-to-b. `abs(ax-bx)<1e-6 && abs(ay-by)<1e-6` selects a FULL
circle, not a zero sweep. Native drawing, fixed-entity, render projection, DXF
and corrected sketch reader agree on that branch. A major270degree Arc must not
be shortened to90. Initial primitive append deliberately refuses near-full
endpoints (documented "use Circle"); that bounded API restriction is not a new
wrong equation. Existing explicit endpoint edits can intentionally change the
actual source into or out of the native full-circle branch.

The confirmed gap was `projectValidationCore.preflight -> io.validateProjectSketch`:
ordinary `validateStrictObject` checked finite fields, but not positive entity
size. The actual preflight function therefore accepted a Segment with a==b,
Circle radius0 or an Arc endpoint at its center. These same records are rejected
by the production solve domain checks. Unconsumed PLANE replay reads sources
through `sketchStorageBundle.readSketch`/`ReadSketch` without invoking solve.
This is a source-confirmed validation-boundary discrepancy, NOT an observed
whole-app Open success or corruption claim; later rendering/profile code could
refuse or classify the record differently.

invalid-domain diagnostics. Append-specific caps and full-Arc refusal stay intact.

by exact known-code whitelists in the validation Worker and the single PM reply
branch, not inferred from message text. All other PM ownership/currentness,
failed-regeneration/history semantics and publication logic are untouched.
No invalid entity is silently dropped or converted. The constant-time domain
checks occur in an existing validation loop; no new heavy UI solve/hash/graph

The helper does not require Arc endpoint-radius equality or a short sweep:
those were not prior generic solver entity-domain requirements. Real internal
ArcConsistency and operation-specific authored branches remain responsible for
solved circular consistency. It never treats coincident Arc endpoints as radius0.
