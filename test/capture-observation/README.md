Two snapshots were charged 8,304,560 bytes; usedJSHeapSize sampled 114,606,821 to 135,284,729 bytes, not peak heap or per-window/process RSS. No forced GC or concurrent-operation load was measured. One unrelated other-engine fixture 1fddd was also sampled but is not current history equality evidence. These measurements are observations, not latency guarantees.

Current source still performs strict viewer serialization, reload and structural equality synchronously for undo/redo. The project capture collects current workspace values, parses/validates each sketch and creates a structured clone on the main thread before async host preparation; manufacturing canonical hash is incremental/Worker-backed, and file Blob restore is preflighted in a Worker. Snapshots are immutable strings with an 8 MiB conservative history budget (one newest oversized transition can remain); async host capture owns a detached clone and guards document, storage, model, expression and lifetime revisions. Neither this observation nor a small-task result proves that high object counts, many-sketch concurrent captures, manufacturing or all admitted input shapes remain responsive. A larger or more geometrically complex actual accepted case should be profiled before choosing a replacement. A possible narrow next step is a bounded, cancellable project-capture Worker receiving captured immutable source strings and returning validated snapshot data, with capture revision rechecks and transferable byte ownership; it would not move live viewer reconstruction off-thread, and must not bypass the atomic publication/currentness and exact save guarantees.
