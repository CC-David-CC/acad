# Many-entity current sketch: browser performance evidence

Actual Chromium/CDP on strict-CSP fixture 20478, app source `a9dafce6e33c442c9ff16d0124c44236711eb5fc`, app SHA256 `41764cb64ae096277673eeb0acddb424642ee977be33e45dcfe0b831d14b6af1`. Compared with requested CAD `154c0aea9`, the complete `web/app/sketcher` and `web/app/cad/projectManager` source trees have no changes; this is not an exact 154c app build. Test `browser.test.cjs` verifies the served app pin. Run with `PUPPETEER_CORE_PATH=/path/to/puppeteer-core CODI_TEST_CDP=http://127.0.0.1:19329 JSKETCHER_TEST_URL=http://127.0.0.1:20478 CODI_RECEIPT=/tmp/capture.json CODI_PROFILE=/tmp/capture-profile.json node test/capture-concurrency/browser.test.cjs`.

The test uses real viewer IO and actual solver: two original segments plus 512 distinct segments with 512 accepted LockPoint relations, 139,364 serialized UTF-8 bytes, no long label. Strictly load and serialize, use real LengthRelation inspect/invoke, exact undo/redo, async changed Save and validated host capture, then create an actual second rectangle sketch and capture both. A separate browser context keeps an independent CAD page and 10 ms timer active throughout the first page's edit/undo/redo measurement. It does not make concurrent mutations, exercise a second high-load window, prove synchronized paint, or assert per-renderer/process isolation. Both owned contexts close in `finally`.

Final sampled run in `receipt.json`: initial load 678.6 ms; inspect 4.1 ms, invoke 515 ms, synchronous undo 676.3 ms, redo 766.8 ms, with exact undo/redo; 4 retained entries charged 839,074 bytes. Long-task observer saw 768–1198 ms tasks, heartbeat maximum 2016 ms across the combined edit, serialization and undo/redo observation window, not a single-operation time. Second page maximum observed heartbeat was 11.4 ms and it remained ready. Save/Worker validation took 1097.6 ms elapsed; successful save disposed the editor history. Host capture took 14.4 ms with one sketch and 10.1 ms with two sketches, after the second sketch was created; capture times include await and are not an isolated serialization profile. JS heap sample 138,981,120 bytes is a single page-reported sample, neither peak nor per-process RSS. This is a finite single-browser observation, not a portable performance guarantee.

`cpu-profile.json` is the actual sampling profile for the primary page during edit/undo/redo only; it excludes initial load, final Save and the two-sketch capture. At 1 ms requested interval, 3,597 samples include browser scheduling/render time; parent-stack counts overlap and must not be summed as distinct time. Notable stacks include `restoreChecked → loadSketch → _loadSketch → finishTransaction → rebuildAdmission → prepareRaw → evaluateAndBuildSolver → evaluatePolynomials → eliminate`, and `invokeByIds → addLengthRelationByIdsAtRevision → runSketchTransaction → finishTransaction → rebuildAdmission → ... → eliminate`. Rendering occurs via `repaint → __drawWorkspace → accept` and Canvas operations. These observations implicate synchronous solver/admission reconstruction and redraw alongside object traversal, not just project JSON capture; they do not by themselves establish the latency of an asynchronous replacement.

A bounded next design should move candidate solve and history replay preparation to the existing headless Worker with immutable source/intent, editor epoch, identity and lifecycle guards; preserve strict admission, exact geometry and rollback, and atomically publish only if still current. It must measure the remaining main-thread graph hydration, observer work and repaint, and separately suppress duplicate redraws where safe. Worker verification must not make unvalidated snapshots authoritative. No product code, UI, Files stack, build or deployment changed in this evidence branch.
