## Ownership and limits

* The normal desktop host Files path calls `restoreSnapshotBytesInEmptyWorkspace` with a genuine Blob and lifetime/signal guard. `projectValidationWorker.ts` checks 128 MiB, parses and preflights in a disposable Worker: tree limit 1,000,000 nodes/depth 128, history/sketches 10,000, and sketch-entry budget 100,000. It returns structured-cloned validated value and pre-serialized model/sketch storage. This is Worker-normalized JSON data, but transferring it to the UI makes an owned UI-realm object; it is not an immutable or versioned Worker-owned model. `restoreParsedSnapshotInEmptyWorkspace` checks operation registration and other model constraints on the UI before `projectService.loadData`; `upgradeIfNeeded` mutates those returned history records to fill defaults/reserve IDs, then `craft.reset` enters ordinary evaluation.
* `restoreSnapshotInEmptyWorkspace` string overload does a Blob-size check and `JSON.parse` on the UI before optional typed-parameter Worker validation; the non-Worker path validates the tree there and stringifies model/sketches for storage. Same-project `projectService.loadStrict` parses storage JSON on the UI. Standalone import's FileReader handler parses on UI. These paths are not represented as Worker-normalized merely because the Blob host path is.
* `craftBundle.ts` accepts privately normalized new command records, verifies feature ID, shares the prior deeply frozen owned accepted history in a new array, and evaluates through `capturePipelineHistory` unless the array has already been marked owned. Publication installs frozen history and computed models together. The narrow `captureAuthoredHistory` used by specific edit/parameter/repair paths intentionally caps 256 entries and 256 KiB before a final JSON string, but is not a general native file limit.
* `runPipeline` and `reset` can receive caller-owned arrays; direct core/debug callers do not have a universal ownership guarantee. `capturePipelineHistory.mjs` has a 10,000-history, 1,000,000-node, depth-128, 256 MiB UTF-16 budget, checks between cooperative batches and never invokes accessors. Before those per-key checks, a single `Reflect.ownKeys` necessarily enumerates the whole container synchronously. The measured valid history array had only 2,000/10,000 keys, so its 0.1/1 ms measurement does not disprove a large-single-container problem. Proxy traps and unversioned mutation during asynchronous comparison are not an atomic snapshot; a plain-object prototype check does not prove absence of Proxy behavior.

The observed real replay cost is a separate issue from the general large-container reflection caveat: candidate `setModels` rebuilds/checks the accumulated registry after each operation. Any optimization must preserve collision and reference/face checks at the point dependent features need them, plus final full validation, failure cleanup, document generation, source and publication currentness. Settled-Promise chains also need explicit task yields and a deadline/currentness check so abort/input can run; merely moving JSON parsing to a Worker does not fix replay or final model-view notification.

A smallest credible future boundary is a versioned, operation-scoped private owner for Worker-parsed native bytes and normalized plain data, with bounded chunked/streamed transfer or worker-produced indexed immutable records and an explicit ownership token. Validate shape/limits before materializing huge UI containers, keep source/epoch/account/window checks across yields, publish one owned history with its evaluated model, and close stale/cancelled candidates. A copied but mutable host object needs an explicit caller ownership/version contract or a real private snapshot; it cannot be authenticated by cooperative comparison alone. There is no incremental JavaScript API for arbitrary Proxy own-key reflection. Preserve existing 128 MiB native and 10,000 history limits; this is a design proposal, not a new blanket lower cap or a claim of universal raw-core safety.
