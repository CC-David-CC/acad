# ARC21: live sketch solver-cache inventory

This is a source inventory and one measured browser baseline, not an implementation or a claim that an unpopulated cache is safe. Source examined: `4ad6a174b`. The test uses the real `997df3dbb` app (`index.bundle.js` SHA-256 `9993b01af9f49ca29aa2eceaa1701489aef01c992ee3a3b38a1a0799f87a9c28`); the app runtime is the same as that source's preceding signed receipt. It creates two same-origin CAD documents in one page and context. While the first viewer synchronously hydrated 514 segments and 512 accepted independent LockPoint constraints, its load took 541.1 ms and a 10 ms timer owned by the second CAD document observed a maximum 641.5 ms gap. This is one run, not a latency guarantee. The second document really loaded CAD; it was not a separate browser context, worker, fake viewer or canvas shim. The test is diagnostic and does not save or publish its generated sketch. Run with `PUPPETEER_CORE_PATH=/path/to/puppeteer-core CODI_TEST_CDP=http://127.0.0.1:19329 JSKETCHER_TEST_URL=http://127.0.0.1:20488 CODI_RECEIPT=/tmp/arc21.json node test/arc21-inventory/same-renderer-browser.test.cjs`.

## Entry points and dependent state

* `sketcher/io.ts` parses, clears and constructs the live graph and calls `parametricManager.finishTransaction`; `history.js` undo/redo/recover call this same path. Both model creation and cache admission occur before the viewer is usable; loading a worker-checked string does not remove the synchronous cache rebuild. `project.js` also prepares systems during sketch lifecycle. The measured example is this ordinary actual load path.
* `parametric.ts` owns stages, transaction and notification ordering, add/remove, prepare and solve. `constr/AlgNumSystem.ts` owns actual polynomial/isolation state, `solveStatus`, conflicting/redundant sets, admission hints, `fullyConstrained`, rollback snapshots and directional `projectedLastValid`. A default successful status and empty conflict sets are not proof of a populated solver.
* `actions/lengthRelationOperation.js` invokes `lengthRelationAdmission.js` inside `sketchTransaction.js` and immediately reads redundancy. Its UI and ID-based paths use that same live manager. The corresponding closed-sketch agent operation in `cad/craft/closedSketchTransitions.ts` already uses Worker transition/inspection and prepared replay, but is restricted to its current source/ancestry, stage, and data contracts; it does not make the open editor asynchronous.
* Other cache consumers are `constraintActions.js` (bulk admission), `editExistingConstraint.js`, `concentricOperation.js`, `diameterOperation.js`, `signedDistanceOperation.js`, `lineRelationOperation.js`, `fixEntityOperation.js`, and `lengthMeasurementRoles.js`. They check accepted versus redundant/conflicting relations and prior state while mutating; changing their result to constructor defaults would silently change behavior. Constraint/dimension deletion also flows through manager removal and admission reconstruction. Annotation and object consumers include `shapes/dim.js`, `shapes/label.ts`, `shapes/sketch-object.ts`, and `shapes/b-spline.ts`.
* Interactive mutations use the live solver: `tools/drag.js` prepares a selected object and performs rough then precise solves; `tools/circle.js` and `tools/ellipse-edit.js` do likewise. `tools/offset.js`, `tools/fillet.js`, `tools/rectangle.js`, `tools/b-spline.js`, and `tools/bezier-curve.js` create/remove geometry or complete transactions. Generator regeneration is coupled to stage solve. Projected-direction last-valid state, rigid-group local frames, generated child identities and branch/domain checks must survive any replacement.
* Agent diagnostics in `cad/sketch/sketchDiagnosticService.ts` already use a disposable Worker and explicitly bound source/boundary/history/currentness; they report a local estimate or unavailable, not full rank knowledge. `cad/sketch/dependentSketchSolve.js` uses Worker solve for dependent parameter regeneration. `cad/craft/rectangleEditing.ts` uses Worker rectangle solve and private candidate replay. These do not populate an open viewer's realm-local solver cache.

## Existing primitives and migration order

1. Retain existing `headless/solve.ts`, `sketchTransition.ts`, `primitiveTransition.ts`, `closedSketchInspection.ts`, and their clients as bounded disposable candidate operations. Their existing policy and resource limits are part of the contract, not a blanket promise for all shapes or constraints. Capture exact source, boundary/frame, stages, external values and editor/document epoch; reject unsupported cases explicitly and preserve the current authoritative graph on any refusal.
2. Implement detached actual graph preparation and a single guarded live installation, with complete stage/object/constraint identity and admission mapping, valid annotation/generator state, batch notifications, and rollback on install failure. Worker evidence is data; it is not a transferable pointer, polynomial or isolation. Preserve source/history and solve-derived fields together, and explicitly represent cache readiness rather than calling unknown state success.
3. Migrate closed inspection/undo/replay and ordinary open-editor initial hydration to that boundary, with cancellation, stale/ABA and same-renderer responsiveness controls. Until each downstream consumer is adapted, it must explicitly wait/refuse when its required live cache is unavailable; never silently skip solve or present fabricated status.
4. Adapt the shared transaction/length admission first, then add/delete/edit constraints and dimensions using the same guarded publication, preserving accepted/redundant/conflict classification and transaction recovery. Extend the Worker operations for each actual schema and generated-object case; do not simply route legacy UI calls into the currently narrower closed-sketch API.
5. Adapt interactive drag and creation separately: rough preview and precise commit, coalescing/cancellation, projected branch/last-valid state and generator dependencies require distinct contracts. Test actual pointer behavior, contradictory edits, undo/redo, native reload and independent same-renderer heartbeat before claiming responsiveness. Existing supported spline, arc, rigid, multi-stage and boundary cases remain supported or explicitly unavailable during transition; no removal or unsupported blanket success.

This inventory is grounded in named active call sites, but does not assert that every dynamically registered plugin or future external caller has been enumerated. Full correctness requires a follow-up call-site and runtime audit as each cache boundary changes. Existing `test/hydration-observation/README.md` documents why the diagnostic skip-admission experiment is not a valid solution.
