# CAD window and worker isolation controls

These are loopback-only tests with independent Chromium contexts. They do not close other contexts or the shared browser.

`browser.test.cjs` uses two real standalone CAD pages under the supplied 19709 fixture with explicit test host-lifetime bindings. It creates independent 100 mm and 120 mm blocks and confirms their actual geometry differs. It sends a real four-corner OCC worker operation in the first page, closes that page before its worker result, and checks that every observed worker target is destroyed. The second page then successfully creates its own centered through-hole. Three further open/create/close cycles leave no worker targets; the full control observed 40 creations and 40 destructions, no CAD Web Locks and zero retained mounts in the remaining page. This page-close test does not exercise the desktop window manager.

`signed-desktop.test.cjs` uses a fresh disposable account on the signed loopback fixture at 19708 and creates two actual jSketcher desktop windows. It uses the real host's lifetime bindings, creates separate 100 mm and 120 mm models, and opens the real unsaved-changes dialog in the first window. While that dialog is open the test invokes the ordinary feature command programmatically, waits until the actual four-corner worker message is sent, then clicks the real Discard changes control. The first window is removed before a worker result, its active worker is explicitly terminated after the close, and its pending command does not publish. The second window's history and geometry remain byte-identical across the first close, and it then completes its own centered cut. Two additional actual window cycles create a block, edit extrusion depth from 20 to 25 mm through the normal history API, and close through the unsaved-changes dialog; each cycle balances observed Worker constructor and terminate calls. The surviving second window retains seven faces, zero mounts and no held/pending CAD Web Locks. This does not claim the complete workflow was manually performed through UI controls, that the document was durably saved, or that a physical device was tested.

In one earlier expanded host run, the second CAD iframe remained `projectLoaded=false` and `hasHostLifetime=false`; the host reported “jSketcher took too long to start” after its existing 60-second deadline. Both in-page WASM resources had completed, but the test's original cleanup closed that context before a deeper trace could be captured. Subsequent equivalent runs passed. There was no blanket Puppeteer request interception in this test. `startup-diagnostic.test.cjs` is the same host control with passive pending-request and error recording; on failure it retains its own context for inspection until interrupted. The lifecycle's `projectLoaded` also waits on the legacy `e0:loader` initialization job, but no exact cause of the intermittent failure is established. No timeout, application source or shared browser was changed.
