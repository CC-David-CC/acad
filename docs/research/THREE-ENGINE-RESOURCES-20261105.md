# Three-engine linear memory and STEP scope

On source `4a3d7aba4`, one fresh Worker per engine executed the same small workload: two overlapping 10×10×10 mm boxes, subtraction, display tessellation, and disposal of all three handles. At ready and after each of those seven commands, the current exported `WebAssembly.Memory.buffer.byteLength` was:

| Engine | Each sampled linear-memory capacity |
| --- | ---: |
| OpenCascade | 16,777,216 bytes (16 MiB) |
| Native Mesh / Manifold | 16,777,216 bytes (16 MiB) |
| SMLib | 33,554,432 bytes (32 MiB) |

All three subtractions returned volume approximately 500 mm³ and 12 display triangles. Each Worker was terminated after its final response. This is a tiny, single-instance control. The values are reserved/current WASM linear-memory capacity, not live allocations, peak memory between samples, browser RSS/PSS, total JavaScript/graphics/asset memory, post-termination reclamation, or a large model estimate. A fixed sample after disposal does not prove absence of leaks. No execution-time comparison is made here.

The harness prepends test-only instrumentation to each exact host-trusted Worker, intercepts `WebAssembly.instantiate`, verifies exactly one instance with one exported `WebAssembly.Memory`, and samples its live buffer length when each existing Worker response is posted. It never reads page JS heap as an engine proxy. The Worker bootstraps are **derived test artifacts**; all three WASM inputs are unchanged and SHA-256 checked. Full production/derived pins and raw sample receipt are in `test/three-engine-resources/pins-20261105.json` and `receipt-20261105.json`. The strict fixture used `default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; worker-src 'self'; connect-src 'self'`, with no reported CSP violations. Tests used a new context within an existing Chromium process, so they are not cold-start, isolated-process, or physical-device measurements.

Reproduce with the 4a3 R730 build or independently matching input bytes. On the test host, set `CODI_RESOURCE_FIXTURE` to a new private absolute directory; set `CODI_OCC_WORKER`, `CODI_OCC_WASM`, `CODI_MANIFOLD_WORKER`, `CODI_MANIFOLD_WASM`, `CODI_SMLIB_WORKER`, and `CODI_SMLIB_WASM` to the exact assets listed in the pin file, then run `node test/three-engine-resources/prepare-fixture.cjs`. Serve that directory using `CODI_ENGINE_TEST_ROOT=$CODI_RESOURCE_FIXTURE CODI_ENGINE_TEST_PORT=20556 python3 modules/engine/mount/strict-csp-server.py`. In a separate shell set `JSKETCHER_TEST_URL=http://127.0.0.1:20556/`, `CODI_TEST_CDP` to an existing loopback Chromium endpoint, and `PUPPETEER_CORE_PATH` to the installed puppeteer-core path; run `node test/three-engine-resources/linear-memory-browser.test.cjs`. The preparation refuses any input hash mismatch and refuses to overwrite derived Workers.

The pinned `smlib-wasm` bridge exposes shape operations and tessellation, not STEP file I/O. The NVIDIA `usd-brep` source describes USD BRep import/export and separate OCC↔USD converters; their existence does not establish a qualified SMLib↔OCC transfer in this application. The existing JSketcher legacy `_ImportStepFile`/`stepImport` entry points refer to OCC-based paths; the repository inventory lists STEP export as not bound in that wrapper. Neither is proof of a usable STEP round trip for Worker-owned SMLib or Manifold models. Reliable STEP needs a separately implemented and qualified precise topology/geometry transfer and translator path, with explicit units, tolerances, identities and unsupported cases. A tessellated mesh is not a substitute for precise STEP. OpenUSD is a possible research interchange route, not an already supported or proven lossless path here. Authored history remains tied to its selected engine; no automatic fallback or conversion is established by this measurement.
